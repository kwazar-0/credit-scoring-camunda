## 1) Зачем существует эта система

Платформа создана с одной целью:

> **Сделать бизнес-решения явными, контролируемыми и аудитопригодными.**

Для кредитного скоринга это критично, потому что:

- решения напрямую влияют на риск и compliance;
- любые изменения должны быть трассируемыми;
- ответственность должна быть назначена явно.

Эти ограничения «вшиты» в архитектуру по умолчанию, а не оставлены на уровне договорённостей команды.

---

## 2) Базовый принцип

> **Системой управляют границы ответственности, а не только структура кода.**

Вместо модели «любой инженер может менять всё» здесь заранее определено:

- **кто может менять решения**
- **кто может менять процессы**
- **кто может менять инфраструктуру**

Каждое изменение должно быть осознанным, проверяемым и контролируемым.

---

## 3) Слоистая архитектура

Платформа разделена на независимые слои:

| Слой | Ответственность | Частота изменений |
| --- | --- | --- |
| Decision (DMN) | Бизнес-правила | Высокая |
| Process (BPMN) | Оркестрация | Средняя |
| Services | Логика исполнения | Контролируемая |
| Infrastructure | Облачная платформа (GCP) | Низкая |

Подробная архитектура и границы слоёв: [architecture](/ru/architecture).

### Ключевое правило слоя

> Каждый слой эволюционирует независимо и принадлежит разным ролям.

Это предотвращает:

- скрытую логику
- случайные cross-layer изменения
- неконтролируемые деплои

---

## 4) Role-based governance (модель 11×6)

Система использует **двумерную модель governance**:

- **11 ролей** — определяют ответственность;
- **6 user domains** — определяют рабочий контур.

### Что это означает

Роль — это не должность.  
Роль — это **контролируемая capability** внутри системы.

Пример:

- Пользователь может менять правила решений
- Но не может деплоить инфраструктуру
- И не может продвигать код в production

Полная расшифровка модели: [gcp-saas-access-matrix-11x6](/ru/gcp-saas-access-matrix-11x6).

### Зачем это нужно

Чтобы обеспечить:

- segregation of duties
- аудитопригодность
- минимально достаточные привилегии

---

## 5) Единая модель доступа

Одна и та же ролевая модель применяется последовательно в:

- GitHub (исходники и workflow)
- GCP (инфраструктура и данные)
- Camunda (процессы и решения)

### Принцип

> Доступ определяется один раз и реализуется везде одинаково.

Это исключает:

- рассинхрон прав
- скрытые обходные пути доступа
- системные security gaps

---

## 6) Git workflow как механизм контроля

Git workflow здесь — не просто процесс разработки.  
Это **контрольный pipeline изменений**.

| Stage | Purpose |
| --- | --- |
| feature | создание изменения |
| develop | интеграция |
| release | валидация |
| main | production state |

См. пошаговое описание: [git-workflow](/ru/git-workflow).

### Ключевое правило

> Продвижение кода между ветками требует проверки и approve.

Это гарантирует:

- ни одно изменение не попадёт в production без контроля
- каждое изменение трассируется

## 7) Infrastructure as Code (Pulumi)

Вся инфраструктура управляется через Pulumi с общим state backend:

```text
gs://credit-scoring-camunda-project-pulumi-state-euc2
```

Детали реализации и команд: [infra-pulumi-iac](/ru/infra-pulumi-iac).

Инфраструктура разделена на независимые стеки:

### infra-core

- VPC, subnet, Private Service Access
- базовый сетевой слой

### infra-data

- storage (GCS), analytics (BigQuery), опционально Cloud SQL
- жизненный цикл данных

### infra-runtime

- GKE (private nodes), Workload Identity
- контур исполнения сервисов и Camunda

### Принцип

> Инфраструктура версионируема, воспроизводима и изолирована по слоям.

---

## 8) Как система ведёт изменения

Типовое изменение проходит путь:

1. Решение или код меняются в рамках определённой роли
2. Изменение проходит через контролируемый Git workflow
3. Инфраструктура/процесс обновляются через Pulumi или Camunda
4. Изменение становится видимым и аудитопригодным

---

## 9) На что система оптимизирована

Платформа оптимизирована для:

- **auditability**
- **controlled change management**
- **clear ownership boundaries**

Платформа не оптимизирована для:

- rapid prototyping
- минимального процессного overhead

---

## 10) Краткий глоссарий (расшифровки)

- **DMN (Decision Model and Notation)** — таблицы и модели детерминированных бизнес-решений.
- **BPMN (Business Process Model and Notation)** — схема процесса, этапы, ветвления, human tasks.
- **Camunda / Zeebe** — оркестрация выполнения процесса и задач.
- **IaC (Infrastructure as Code)** — декларативное управление инфраструктурой через код (в этом репо — Pulumi).
- **SoD (Segregation of Duties)** — разделение обязанностей и прав между ролями.
- **PII (Personally Identifiable Information)** — персональные данные, требующие защиты и маскирования.

---

## 11) Итог

Система жёстко проводит три ограничения:

1. **Разделение ответственности по слоям**
2. **Явный контроль доступа через модель ролей (11×6)**
3. **Контролируемый поток изменений через Git и инфраструктурные pipeline**

> Если изменение нельзя объяснить, отследить и атрибутировать,  
> ему не место в системе.
